# ASR Pipeline: гейт качества поверх распознавания

## Что это

Локальный CLI-пайплайн для команды, которая получает аудио и должна решить,
можно ли отдавать распознанный текст и саммари дальше. Это **гейт качества поверх ASR**,
а не новая модель распознавания и не оценка точности по эталону.

Поток: вход → ASR → gate → route → точечный repair → повторный gate →
экстрактивное summary с guard → verify. Gate сопоставляет энергетическую
активность, интервалы текста, язык, качество сигнала и согласие гипотез.
Каждый шаг оставляет JSON-артефакты; итоговая карточка показывает причины,
а не выдуманный процент точности. Подробности передачи команды — `INTEGRATION.md`.

## Быстрый старт

Нужны Bash и отдельно подготовленный `uv` в PATH. Сначала выполните provisioning
ниже: готовая `.venv` не является входным требованием. Для repair нужен `ffmpeg`
в PATH; `ffprobe` используется для ingest, с fallback на soundfile. Веса и внешние
x20 venv не устанавливаются автоматически и не копируются с другой машины.

Из корня проекта:

```bash
bash scripts/provision.sh
bash scripts/smoke.sh
.venv/bin/python scripts/check_portable.py
bash scripts/check_docs.sh
bash run.sh --audio ./audio.wav --out ./run --engine whisper_ct2
```

Последняя команда требует ваш `audio.wav` и **заранее локально доступную** модель
CTranslate2 `large-v3`. Адаптер задаёт `local_files_only=True`: без весов он
завершится ошибкой, а не скачает модель. Вы можете задать локальный каталог
весов через `--model` внутри `cmd` своего engines-конфига. Smoke не требует
ни весов, ни x20, ни исходной записи: он создаёт синтетический WAV и использует
`fixtures/whisper.json` и `fixtures/kts.json`. Это проверка программного потока,
а не проверка качества ASR на живом аудио.

Для четырёх x20-движков задайте `ASR_X20_ROOT` в окружении и выберите движок:

```bash
ASR_X20_ROOT=/srv/asr/x20 bash run.sh --audio ./audio.wav --out ./run --engine gigaam
```

`run.sh` выставляет `ASR_PY_ROOT` в собственный каталог, проверяет `.venv`,
разворачивает env-шаблоны в `<out>/.engines.resolved.json` и запускает
`asr_pipeline.py run`. Этот файл сохраняется для verify/resume; не удаляйте его.
`ASR_X20_ROOT` — единственный входной корень x20, `X20_ROOT` — синхронизированный
выходной alias совместимости (не отдельная настройка). При прямом запуске
адаптер берёт `ASR_X20_ROOT`, а без него читает default из `engines.json`;
при отсутствии однозначного default требует задать переменную. По умолчанию: `audio.wav` и `run` относительно текущего
каталога, первый движок конфига (`gigaam`), `language=ru`, `vad=energy`,
`lid=declared`, `budget-frac=0.35`. Аргументы CLI перекрывают defaults;
доступны `ASR_AUDIO`, `ASR_OUT`, `ASR_ENGINE`. `declared` — заявленный язык,
**не независимая проверка LID**. Для реального LID/VAD явно выберите
`--lid whisper --vad silero`; это уже модельный прогон.

При `--engine whisper_ct2` обёртка также направляет repair-алиас `whisper`
на CT2 в развёрнутой конфигурации этого прогона: fallback не требует x20 даже при ремонте.
Исходный `engines.json` при этом не изменяется. Без `--resume` повторный run
может очистить свои прежние выходные стадии: выделяйте каждому заданию свой `--out`.

## Provisioning и offline-режим

`bash scripts/provision.sh` создаёт `.venv` командой `uv venv --python 3.12 .venv`,
затем вызывает `uv pip install --python .venv/bin/python --require-hashes
--only-binary :all: --strict -r requirements-lock.txt`. По умолчанию оба шага
offline: локальный Python 3.12 и заранее наполненный кэш uv обязательны.
При отсутствии Python/дистрибутивов скрипт выдаёт ошибку, не выходит в сеть,
не ставит uv/ffmpeg и не запускает ML. Существующая рабочая `.venv` Python 3.12
сохраняется; другая/повреждённая среда не перезаписывается.

Только по решению оператора разрешите загрузку Python/пакетов:

```bash
bash scripts/provision.sh --online
```

`requirements-lock.txt` содержит полный transitive closure установленной среды
**CPython 3.12 / macOS arm64**, все версии и SHA-256 дистрибутивов из локального
кэша реестра uv. Это не универсальный lock для Windows/Linux и не lock x20.
Для другой платформы нужен отдельно проверенный lock. Чистая машина без сети
потребует заранее перенесённого кэша uv/разрешённых дистрибутивов и Python;
сам файл lock не содержит wheels. Пересоздание среды из пустого кэша этим
handoff не проверялось: установка пакетов при подготовке была запрещена.

`run.sh` принудительно экспортирует `HF_HUB_OFFLINE=1` и `TRANSFORMERS_OFFLINE=1`;
`bash run.sh --online --audio ./audio.wav --out ./run --engine whisper_ct2`
снимает оба флага только для этого процесса. Это не сетевой sandbox: отдельно
ограничьте сеть ОС при строгом требовании. `local_files_only=True` CT2/LID
не отключается этим флагом, веса всё равно нужны локально. Прямой Python CLI
не наследует политику обёртки автоматически: экспортируйте оба флага сами.
Сведения о весах, revisions и SHA-256 — `MODEL_MANIFEST.md`; юридические
ограничения — `LICENSES.md`.

## Проверка перед передачей

После provisioning, из корня пакета (команды не запускают ASR-модели):

```bash
export HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1
.venv/bin/python -m pytest -q
bash scripts/smoke.sh
.venv/bin/python scripts/check_portable.py
bash scripts/check_docs.sh
.venv/bin/python asr_pipeline.py verify --run ./run-final
```

`run-final` — уже существующий локальный прогон; verify читает его WAV/артефакты
и записывает `60_verify/report.json`, но не делает inference. Если прогон или
исходный WAV не переданы, этот пункт **не проверен**, а не PASS. На новой машине
проверьте новый согласованный run и его provenance; не изменяйте исторические
артефакты ради зелёного verify. Smoke проверяет ожидаемые exit 2 стадий и оговорку,
не качество моделей. `check_docs.sh` проверяет обязательные разделы, ссылки на
файлы поставки и упомянутые флаги по реальному `--help`, без install/ML/сети.
Успех технических команд не закрывает решения по правам из `LICENSES.md`.

## Артефакты

Все пути ниже относительны `--out`. Отсутствие repair/summary допустимо,
если стадия пропущена по записанной причине. Не ищите «самый новый» файл:
используйте указатели `run.json`.

| Каталог/файл | Контракт |
|---|---|
| `00_input/manifest.json` | `asr.input/1`: путь, SHA-256, длительность, sr, channels входа |
| `.engines.resolved.json` | Сохраняемый run.sh входной конфиг; нужен повторным verify/resume |
| `00_input/engines.json` | Снимок разрешённой конфигурации движков этого прогона |
| `10_asr/segments.json` | Первичная нормализованная гипотеза `asr.segments/1` |
| `10_asr/engine/` | Сырой вывод выбранного адаптера |
| `10_asr/NAME.json`, `10_asr/ensemble/report.json` | В режиме ансамбля: гипотезы, голоса, n_votes, enabled, исключённые движки |
| `20_gate/trust.json`, `trust.md`, `vocab.md` | `asr.trust/2`, читаемая карточка и кандидаты словаря |
| `30_route/route.json` | `asr.route/1`: шаги, блокировки, бюджет, допуск summary |
| `40_repair/plan.json`, `additions.json`, `segments_merged.json` | План `asr.repair.plan/1`, добавления, исправленный текст; также cuts/engine и attempt-отчёты |
| `21_gate_after/trust.json` | Повторный gate; дальнейшие попытки в `21_gate_after/aN/` |
| `50_summary/summary.md`, `summary.json` | Допущенный пересказ и `asr.summary/1`; при отказе возможен `summary.rejected.md` вместо summary.md |
| `60_verify/report.json` | `asr.verify/1`: нарушения инвариантов и результат проверки |
| `run.json` | `asr.run/1`: журнал стадий, итог, `effective_transcript`, `final_trust`, unresolved_s |
| `logs/` | Команды, stdout/stderr и коды стадий; могут содержать текст записи |

## Коды причин

Каждая причина содержит `code`, `severity` (`warn` или `block`), `detail`,
`intervals` (секунды). Любой `block` даёт gate-вердикт `failed`;
только предупреждения дают `partial`, отсутствие причин — `ok`.

| Код | Смысл и маршрут |
|---|---|
| `LANGUAGE_MISMATCH` | Язык не совпал; остановка и ручная проверка |
| `LOW_LEVEL` | Тихий сигнал; нормализация для level-sensitive движка |
| `CLIPPING` | Отсчёты на пределе; не усиливать, при тяжёлом клиппинге блокировать |
| `VAD_UNRELIABLE` | VAD пропускает активность; перейти на энергетический детектор |
| `TAIL_UNCOVERED` | Активность после последнего сегмента; дописать хвост |
| `LOW_COVERAGE` | Низкое union-покрытие; второй движок/другая сегментация |
| `SPEECH_GAP` | Дыры активности без текста; точечное повторное декодирование |
| `LOW_AGREEMENT` | Гипотезы расходятся; арбитраж и прослушивание |
| `LOW_INFORMATION` | Пустые/однословные вырожденные сегменты; пересегментация и повтор |

Неизвестная причина блокирует route как `UNKNOWN_REASON` (fail-closed).
Бюджет по умолчанию — 0.35 длительности аудио; один план не означает,
что все предлагаемые шаги уже исполнены. Подробнее о deferred — в интеграции.

## Exit-коды

| Код | Значение |
|---|---|
| `0` | `ok`: операция успешна, для run текст допущен при пройденном verify |
| `2` | `partial`: артефакты есть, нужны оговорки и проверка спорных мест |
| `3` | `failed`: качество/инварианты не прошли, не публиковать summary |
| `4` | `blocked`: нужен человек, маршрут или guard остановил выдачу |
| `64` | Ошибка аргументов/конфигурации; исправить запуск |
| `1` | Внутренняя/операционная ошибка, включая сбой дочернего процесса |

Важно: сам `asr_gate.py` возвращает только `0/2` для завершённой оценки,
в том числе `2` при `verdict=failed`. Читайте JSON, а не только статус процесса.
`verify` возвращает `0/3`: корректные артефакты partial дают verify exit 0,
но исходный run/status остаётся exit 2. `route` и `summarize` при partial тоже
возвращают 2, не 0. Отказ guard переводит итог run в blocked/4; сбой verify —
failed/3. `--legacy-exit` у run/status схлопывает `3/4` в `2`;
в новых интеграциях этот флаг не нужен. Ошибки внешних стадий могут стать
`E_STAGE_FAILED`/exit 1 на фасаде — подробности и ограничения в `INTEGRATION.md`.

## Формат engines.json

Файл — плоский JSON-объект `имя → конфигурация`. В поставке **четыре участника
ансамбля** (`gigaam`, `whisper`, `parakeet`, `qwen`) и отдельный
`whisper_ct2` для CPU/int8 fallback без x20. Первый движок — default.

| Поле | Тип и назначение |
|---|---|
| `cmd` | Массив argv (рекомендуется) или строка, разбиваемая shlex; interpreter, script, аргументы |
| `output` | Имя выходного JSON относительно `{out}` |
| `model` | Строка идентификатора модели для provenance; реальный выбор задаёт адаптер/его аргументы |
| `level_sensitive` | bool: чувствительность к уровню сигнала |
| `timeout_s` | Положительный таймаут subprocess в секундах |
| `ensemble` | bool: участие в ансамбле; true у четырёх x20, false у CT2 |
| `family` | `torch` у GigaAM, `mlx` у остальных x20, `ct2` у fallback |

В `cmd` используются `{audio}` (входной WAV), `{out}` (каталог результатов),
`{language}`. На стадии repair тоже передаётся каталог `{out}`, не имя файла.
Подстановки `${ASR_PY_ROOT}` и `${ASR_X20_ROOT:-/Users/Ivan/PycharmProjects/Codex/2026-10-27/x20}`
разворачиваются обёрткой **до** запуска Python-модулей, без eval и без shell=True.
Первый путь — корень этой поставки, второй — корень уже подготовленного x20.
Жёстко заданный путь разрешён только как этот конфигурационный fallback и в docs.
В стороннем оркестраторе делайте такую же безопасную подстановку сами.

Интерпретатор GigaAM — `${ASR_X20_ROOT}/work/ru_asr/venv/bin/python`;
Whisper/Parakeet/Qwen — `${ASR_X20_ROOT}/work/venv/bin/python`;
CT2 — `${ASR_PY_ROOT}/.venv/bin/python`. Все четыре x20 используют
`${ASR_PY_ROOT}/engines/x20_engine.py` с `--engine NAME --window 20`.
Поле `ensemble=true` описывает состав, но само по себе **не запускает**
четыре процесса: без явного запроса run выбирает один `--engine`. Для ансамбля:

```bash
bash run.sh --audio ./audio.wav --out ./run-ensemble --ensemble all
```

Доступен и список `--ensemble gigaam,whisper,parakeet,qwen`. Отказ любого движка,
включая выбранный основной, допускается: неудачные исключаются с notes. При двух
и более успешных включается medoid; при одном используется единственная
выжившая гипотеза (не обязательно исходный primary); при нуле run падает: проверяйте
`run.json.ensemble.n_votes/enabled`, не обещайте четыре голоса по одному флагу.
Независимые гипотезы также можно передать `--peer NAME=PATH`; готовые JSON
объединяются `asr_ensemble.py --segments NAME=PATH ... --out DIR`.

## Свой движок

1. Адаптер принимает входной WAV и создаёт JSON `asr.segments/1` либо совместимый
   legacy JSON для `adapt_legacy.py`. Непустой текст, корректные секунды,
   монотонные start, уникальные id и ссылка на тот же вход обязательны.
2. Добавьте запись в собственный engines-конфиг, явно задав **cmd + output + ensemble**
   и остальные поля таблицы; укажите реальный interpreter и существующий script.
3. Вызовите `bash run.sh --engines ./my-engines.json --engine my_asr --audio ./audio.wav --out ./run-my`.
   Собственный конфиг не обязан содержать поставляемые пять движков; штатный
   portability check проверяет именно комплектную конфигурацию из `engines.json`.

Пример записи (путь и имя адаптера нужно заменить на свой существующий файл):

```json
{
  "my_asr": {
    "cmd": ["${ASR_PY_ROOT}/.venv/bin/python", "${ASR_PY_ROOT}/engines/my_asr.py", "--audio", "{audio}", "--out", "{out}/segments.json", "--language", "{language}"],
    "output": "segments.json", "model": "my-local-model", "level_sensitive": false,
    "timeout_s": 900, "ensemble": true, "family": "torch"
  }
}
```

## Ограничения

- **Нет эталона и нет WER/CER.** Покрытие и согласие движков — диагностические
  признаки, не точность; несколько моделей могут согласованно ошибиться.
- Покрытие — пересечение union интервалов текста с энергетической активностью;
  шум может попасть в знаменатель. Дыры короче 1 с не входят в uncovered_all.
- **Окно 20 с маскирует внутрооконные потери**: непустой текст закрывает весь
  интервал окна, даже если часть слов внутри потеряна. Это особенно важно для
  x20-адаптера и medoid-ансамбля; нужны прослушивание/более точные таймкоды.
- x20 MLX и GigaAM/MPS требуют совместимой Apple Silicon/macOS-среды. CT2 —
  отдельный CPU fallback, но локальные веса и совместимые бинарные зависимости
  тоже обязательны. Общий lock не фиксирует torch/MLX-окружения x20.
- x20-адаптер ориентирован на русский язык и подготовленный 16 кГц mono WAV;
  `--language` в интерфейсе не обещает поддержку всех языков всеми моделями.
- Summary экстрактивное, не LLM: предложения с числами вне trust могут быть
  отброшены. Guard не доказывает смысловую верность решений и задач.
- `--resume` не является полной защитой от подмены артефактов. Перед выдачей
  запускайте verify и сверяйте его независимый пересчёт с чеклистом приёмки.
- `check_portable.py` проверяет Python, включая tests: персональные пути запрещены,
  синтетические `/x`, `/abs` и переносимые системные пути разрешены. Единственное
  исключение конфигурации — default `ASR_X20_ROOT` в `engines.json`; в адаптере
  датированного fallback нет. Зелёный preflight не доказывает inference моделей.
- Аудио, транскрипты и логи могут содержать персональные данные. Ограничьте права
  на run-каталоги; не публикуйте их вместе с исходниками.
